# 10 性能回归排查

> 决策树第 1 步「性能回归」分型的展开打法：延迟/吞吐劣化、CPU 占用异常的识别、定位与根因。
> 本文转录自 spec §4「按症状分型（性能回归）」+ §5「知识源与优先级」。

**核心原则（先记住）**：性能问题是「量」的问题，不是「错」的问题——没有 oops，全靠计数器对比。先测（perf stat 拿基线数字）→ 再定位热点（perf record/top）→ 再下钻（function_graph/bpftrace/火焰图）。**测量驱动，别瞎优化**：每个优化前后都要用 `perf stat` 对比，用数字证明变快，否则不做。

## 工具一：perf stat —— 对比基线、总览计数器

**何时用**：第一步。量化「劣化多少」，给 CPU 周期、指令数、缓存未命中、上下文切换等一个总数，作为优化前后的对比基线。

**关键命令**：

```bash
# 跑一个命令，统计默认计数器（cycles/instructions/branch/cache-miss 等）
perf stat <command>
# 指定关心的计数器：IPC 看 cycles+instructions，缓存看 cache-misses/references
perf stat -e cycles,instructions,cache-misses,cache-references <command>
# 重复 3 次取平均，抵消噪声
perf stat --repeat 3 <command>
# 针对已运行的进程采样
perf stat -p <pid> sleep 5
```

**怎么读输出**：重点看三个比值：

- **IPC = instructions / cycles**：明显低于 1 说明 CPU 大量空等（缓存未命中 / 锁竞争 / 分支预测失败）。
- **cache-miss rate = cache-misses / cache-references**：高说明访存模式差，数据没命中缓存。
- **context-switches**：异常高说明线程/任务频繁切换或锁竞争导致的睡眠唤醒。

> 出处：`tools/perf/Documentation/perf-stat.txt`

## 工具二：perf record + perf report —— 找热点函数

**何时用**：确定了「慢」，要回答「时间花在哪个函数」。采样（periodic sampling）拿调用栈，事后离线分析。

**关键命令**：

```bash
# 采样并记录调用栈（-g 拿调用链，-F 设采样频率）
perf record -g -F 999 -a -- <command>     # -a 全机；或 -p <pid> 只测某进程
# 交互式/文本查看热点
perf report            # TUI，按函数聚合
perf report --stdio    # 纯文本
```

**怎么读输出**：`perf report` 默认按 `Overhead` 降序列出各函数占的采样比例（`self`=函数自身、`children`=含被调者）。顶部那个占比最高的函数就是 CPU 热点。按 `+` 展开调用栈，看它是在「自己算」还是「被谁调」；若热点集中在 `_spin_lock`/`_raw_spin_lock_irqsave` 等锁函数，转去查锁竞争。

> 出处：`tools/perf/Documentation/perf-record.txt`、`perf-report.txt`

## 工具三：perf top —— 实时看热点

**何时用**：系统正在跑、想立刻看「现在哪在烧 CPU」，不用等采样结束。

**关键命令**：

```bash
perf top          # 实时刷新，按函数开销排序
perf top -g       # 带调用链
perf top -e cache-misses   # 换计数器，看谁在制造缓存未命中
```

**怎么读输出**：类似 `top` 的实时列表，`Overhead` 列实时跳动；长期霸榜的函数即当前瓶颈。适合现场快速指认，但结果是快照，深入仍要 `perf record`。

> 出处：`tools/perf/Documentation/perf-top.txt`

## 工具四：ftrace function_graph —— 看每个函数调用耗时

**何时用**：热点已缩小到某条调用路径，想知道「链上每一步各花多少」，尤其对比同类路径里哪一步突然变长。

**关键命令**：

```bash
echo function_graph > /sys/kernel/tracing/current_tracer
echo 'my_func*' > /sys/kernel/tracing/set_ftrace_filter   # 只看这条路径
echo <pid> > /sys/kernel/tracing/set_ftrace_pid
cat /sys/kernel/tracing/trace
```

**怎么读输出**：每个函数一行，缩进表层级，右列 `DURATION` 表耗时；`}` 闭合行上的时长是该函数**含子调用**的总耗时（如 `3) ! 140.417 us | } /* __schedule */`）。`!`/`#` 等前缀标记耗时超阈值的异常长调用——顺着最长的 `}` 行往下找，就是耗时元凶。

> 出处：`Documentation/trace/ftrace.rst`（`function_graph` tracer、DURATION 列、`!`/`#` 阈值标记）

## 工具五：bpftrace 自定义探针 + 火焰图

**何时用**：内置 tracer 覆盖不到的定制需求（某函数延迟直方图、某变量的分布），或要把 `perf record` 的结果可视化成火焰图。

**bpftrace 关键命令**（低开销动态插桩，例子）：

```bash
# 统计 vfs_read 延迟分布（纳秒直方图）
sudo bpftrace -e 'kprobe:vfs_read { @start[tid] = nsecs; }
                  kretprobe:vfs_read /@start[tid]/ { @us = hist((nsecs - @start[tid])/1000); delete(@start[tid]); }'
```

**火焰图**：`perf record -g -a -- sleep 30` → `perf script > out.perf` → `stackcollapse-perf.pl out.perf | flamegraph.pl > out.svg`。火焰图横轴=采样占比、纵轴=调用栈深度，宽的「塔」就是耗时大户，一眼看出热点在调用栈哪一层。

**怎么读结果**：bpftrace 直方图看延迟分布（长尾/P99 突刺）；火焰图找「又宽又高」的栈——宽=占采样多，高=调用深，中间某层特别宽就是瓶颈层。

> 出处：bpftrace 用法见 `Documentation/bpf/redirect.rst`（官方示例）；火焰图由 `perf script` 输出生成（`tools/perf/Documentation/perf-script.txt` 提到 flamegraph 用途）

## 常见根因 + 修复注意

**常见根因**：

- **锁竞争**：`perf report` 热点落在 `_spin_lock`/`mutex_lock`；`perf lock` 或 `perf c2c` 进一步看是哪把锁、哪个 cacheline。
- **缓存未命中 / 虚假共享（false sharing）**：多核反复写同一 cacheline 的不同字段，互相失效对方缓存 → `perf c2c`（HITM 分析）可定位共享热点行。
- **不必要的拷贝**：热点落在 `memcpy`/`memmove`，说明数据被反复搬。
- **频繁中断 / 软中断**：`perf top` 里 irq handler 占比高，或 `perf stat` 的 `context-switches`/软中断计数异常。
- **O(n²) 算法**：数据规模上去才慢，热点集中在某几个嵌套循环。
- **虚假共享**（另见上）：cacheline 颠簸导致 CPU 空转。

**修复注意**：

1. **测量驱动**：优化前 `perf stat` 记基线，改完再 `perf stat` 对比，用 `--repeat` 取均值排除噪声；没数字的优化不算数。
2. **先抓最大热点**：`perf report` 顶部那个函数，改完再重测，别一次改一堆。
3. 锁竞争优先看能否缩小临界区/换 RCU/免锁结构；缓存问题看结构体字段重排（`__cacheline_aligned`）或填充对齐。

> 出处：虚假共享/缓存未命中定位见 `tools/perf/Documentation/perf-c2c.txt`（Shared Data C2C/HITM Analyzer）
