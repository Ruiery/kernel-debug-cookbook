# 09 行为错误定位

> 决策树第 1 步「行为错误（不崩但结果错）」分型的展开打法：系统不崩、不挂，但结果/行为对不上预期（逻辑错）。
> 本文转录自 spec §4「按症状分型（行为错误）」+ §5「知识源与优先级」。

**核心原则（先记住）**：行为错误没有 oops 现场，唯一的线索是「预期 vs 实际」的差异。先把它收敛成「从哪个 commit 开始错」或「哪个函数算错了」，再谈为什么。手段由低扰动到高扰动：git 历史（零扰动）→ KUnit 单测隔离 → WARN_ON/pr_info 打印关键状态（最后才用）→ ftrace 确认走了哪条分支。

## 工具一：git bisect —— 二分定位引入错误的 commit

**何时用**：行为曾经是对的、某个版本之后变错，且能明确给出「好的」和「坏的」两个 commit（哪怕只靠「这版能跑/这版不能跑」）。

**关键命令**：

```bash
git bisect start
git bisect bad <坏 commit>
git bisect good <好 commit>
# git 自动 checkout 到中间点，复现测试后标注：
git bisect bad    # 这版还是错
# 或
git bisect good   # 这版是对的
# 重复直到定位，最后：
git bisect reset  # 回到原始 HEAD
```

**怎么读结果**：收敛到的那一个 commit 就是「引入行为的改动」，`git show <commit>` 看它动了哪几行，往往一眼看出逻辑错。

**注意**：内核有大量历史 commit，二分要有可重复的「复现脚本」作为判据，否则 `good/bad` 标注不可信。定位到回归 commit 后，提交修复时补 `Fixes:` 标签（前 12 位 sha）便于 stable 回溯。

> 出处：`Documentation/process/submitting-patches.rst`（`Fixes:` 标签 + `git bisect` 定位回归的说明）；`git bisect` 官方用法见 pro-git（内核 Documentation 无专页）

## 工具二：KUnit 单测 —— 把错误隔离到具体函数

**何时用**：已经怀疑某几个函数算错，想不跑整机、直接在 UML/QEMU 里对单个函数设断言，确定「哪个输入 → 哪个输出」错了。

**关键命令**：

```bash
# 跑测试（默认 UML，kunit_tool 自动 config/build/run）
./tools/testing/kunit/kunit.py run
# 只跑某个 suite 的某组 case（glob 过滤）
./tools/testing/kunit/kunit.py run 'my_suite*'
# 解析已有 dmesg 里的 TAP 结果
./tools/testing/kunit/kunit.py parse /var/log/dmesg
```

**写断言**（`KUNIT_EXPECT_*` 失败不中止、`KUNIT_ASSERT_*` 失败立即终止）：

```c
static void my_test_basic(struct kunit *test)
{
    KUNIT_EXPECT_EQ(test, 2, add(1, 1));          /* 期望值在前 */
    KUNIT_ASSERT_NOT_ERR_OR_NULL(test, buf);      /* 分配失败立即停 */
}
/* 注册 suite */
static struct kunit_case my_cases[] = { KUNIT_CASE(my_test_basic), {} };
static struct kunit_suite my_suite = {
    .name = "my", .test_cases = my_cases,
};
kunit_test_suite(my_suite);
```

**怎么读结果**：TAP 格式输出，`ok N - test_name` 通过、`not ok N - test_name` 失败并给出 `KUNIT_EXPECT_EQ` 的「期望 vs 实际」值。把失败的那组输入单独拎出来，就是行为错误的精确复现，比整机复现小几个数量级。静态函数可通过 `#ifdef CONFIG_MY_KUNIT_TEST` 条件 `#include` 测试文件来覆盖。

> 出处：`Documentation/dev-tools/kunit/usage.rst`（EXPECT/ASSERT 宏、suite 注册、测静态函数）；`Documentation/dev-tools/kunit/run_wrapper.rst` + `running_tips.rst`（`kunit.py run/parse`、glob 过滤）

## 工具三：WARN_ON / pr_info —— 打印关键状态（先检测、后 dump）

**何时用**：bisect 定位到 commit、KUnit 缩小到函数后，仍要确认「运行时走到这里时，某个变量/条件到底是多少」。遵循决策树第 0 号原则：**printk 排最后**，且用「先检测、后 dump」——异常条件已满足才打，别持续刷屏。

**关键写法**：

```c
/* 条件不成立就 WARN，并带出关键状态，方便事后一次性 dump */
if (WARN_ON(state != STATE_READY))
    pr_info("unexpected state=%d, idx=%d, cnt=%ld\n", state, idx, cnt);
```

**怎么读输出**：`WARNING: CPU: N PID: ... at <file>:<line> <func>+0x.../0x...` 带调用栈（`dump_stack`），结合你塞进去的 `state/idx/cnt` 值，确认「到底是哪个条件判断反了、哪个边界差一」。

**注意**：`pr_info` 可配 `CONFIG_DYNAMIC_DEBUG` 用 `echo 'module foo +p' > /sys/kernel/debug/dynamic_debug/control` 按模块/行开关，不必重编；WARN_ON 在 panic_on_warn 配置下会 panic，别在热路径埋。

> 出处：`include/asm-generic/bug.h`（`WARN_ON` 宏族）；`Documentation/admin-guide/bug-hunting.rst`（WARNING/oops 现场解码）；`Documentation/admin-guide/dynamic-debug-howto.rst`（dyndbg 开关 pr_info）

## 工具四：ftrace function tracer —— 确认走了哪条分支

**何时用**：结果对错取决于「运行时到底进了 if 的哪一支 / 调了哪个函数」，想看函数实际调用序列。

**关键命令**：

```bash
# 挂 function tracer（零改代码，看谁调了谁）
echo function > /sys/kernel/tracing/current_tracer
# 只看怀疑的函数，缩小范围
echo 'my_func' > /sys/kernel/tracing/set_ftrace_filter
# 限定到某个进程，排除噪声
echo <pid> > /sys/kernel/tracing/set_ftrace_pid
# 看结果
cat /sys/kernel/tracing/trace
```

**怎么读输出**：`trace` 里按时间列出「哪个 CPU 进入了哪个函数」。对照你的 if/else，看运行时实际进的是不是你预期的分支；若某条分支的函数根本没出现，就说明条件判断/调用点写错了。

> 出处：`Documentation/trace/ftrace.rst`（`function` tracer、`set_ftrace_filter`、`set_ftrace_pid`）

## 常见根因 + 修复注意

**常见根因**：

- **条件判断错**：`&&` 写成 `||`、`>` 写成 `>=`、判断的变量不是你想要的那个。
- **边界 / off-by-one**：循环 `< N` 与 `<= N`、数组下标越界一、长度算错。
- **状态机转换漏**：某个事件/错误路径忘了置状态位，导致后续分支走错。
- **初始化顺序错**：依赖的值在被读取之后才初始化（顺序颠倒），读到旧值/零值。

**修复注意**：

1. **先锁 commit、再锁函数、再读代码**，别一上来通读全模块。
2. **补 KUnit 回归测试**：把「之前算错的输入」固化成 `KUNIT_EXPECT_EQ` 用例，防止再次回归；这是行为错误修复的收尾必备动作。
3. 修条件/边界类错误时，把「正确值」写清楚再改，避免修完又差一。
