# 00 决策树

> 定位根因的主入口。按顺序走：第 0 号原则 → 第 0 步（上游/魔改）→ 第 1 步（症状分型）→ 崩溃细分。
> 本文转录自 spec §4「方法论（决策树）」。

## 第 0 号原则：最小扰动优先

按对系统的扰动从低到高选手段，**printk 排最后**：

1. **零扰动**：读已有 oops/dmesg/vmcore、读源码、查 git。
2. **最小活体观测**：单个 tracepoint / kprobe / ftrace 单函数。
3. **专抓现行的检测器**：KASAN / KCSAN / lockdep（在污染发生点确定性抓现行）。
4. **最后才 printk**（会改时序、掩盖竞态；且 printk 自身可能死锁，见 CVE-2022-49441）。

**技法：先检测、后 dump** —— 埋检测逻辑，异常条件已满足才 dump，而非持续 printk。

> 出处：LKML Valdis Kletnieks（https://lkml.org/lkml/2009/4/28/644 ）；Paul McKenney perfbook / LPC 2023。printk 死锁风险见 CVE-2022-49441。

## 第 0 步：上游 or 魔改（决定后面所有动作）

```
这段代码是上游原生，还是魔改过？
├─ 上游原生 → 标准流程
│    · git blame / git log 可信（message 详细）
│    · Documentation 可用
│    · "搜相关 patch" 直接有效（→ methodology/02-搜相关patch.md）
└─ 魔改 → 叠加"特定条件"（只此分支）
     · git 历史当线索、不当真相
     · 溯源：拿特征行当指纹，跨版本+跨arch搜真实出身
     · 跨 arch 内存序检查（x86 强序 vs ARM 弱序，屏障假设是否变）
     · 运行时事实是唯一真相（KASAN/crash/tracepoint）
     · 找清相对哪个 baseline（版本+arch）分叉的
```

## 崩溃细分

```
oops 现场是凶手还是受害者？
├─ direct 故障（null 解引用/死锁/明显逻辑错）→ 缩到 50 行读代码
└─ 内存生命周期（越界/UAF/double-free/未初始化/流动转化）
     → 立刻上工具，别再读代码猜：
        · 越界/UAF/double-free  → KASAN（报真正的坏访问+凶手栈）
        · 初始化没做干净        → KMSAN
        · 谁分配的/什么状态     → page_owner + mm tracepoints
        · slab 邻居写坏         → slub_debug / SLAB poisoning
```

**关键认知**：内存类故障的 oops 现场是受害者，根因在内存生命周期历史里，代码阅读在原理上找不到，必须靠运行时工具把"受害者地址"翻译回"凶手地址"。

详细打法见 `methodology/01-内存问题排查.md`。

## 延伸 playbook（按子系统下钻）

七类症状之外，CPU/内存魔改高频的子领域，单独成册。按症状归类到上面的分支后再下钻：

| 子领域 | 解决什么问题 | 详见 |
|--------|-------------|------|
| 内存耗尽 / OOM | 「用光内存」——读 OOM 报告、`/proc/meminfo` 分项、水位线、cgroup 限额 | 12-OOM与内存耗尽.md |
| 内存泄漏 | 「该释放没释放」——kmemleak 拿分配栈、refcount 泄漏 | 13-内存泄漏kmemleak.md |
| 调度器调试 | 「谁该跑没跑/跑太久/迁错核」——`/proc/sched_debug` + sched tracepoint | 14-调度器调试.md |
| 中断 / 软中断 | 中断风暴、关中断太久、softirq 堆积——`/proc/interrupts` + irqsoff | 15-中断与软中断分析.md |
| 延迟分析（RT） | 最坏延迟/长尾抖动（区别于吞吐）——osnoise/timerlat/hwlat | 16-延迟分析RT.md |
| 栈溢出 | 内核栈用超（独立于内存生命周期的崩溃根因）——VMAP_STACK guard/STACKPROTECTOR | 17-栈溢出定位.md |

> 内存三兄弟关系：01（损坏型）≠ 12（耗尽型）≠ 13（泄漏型），症状不同、工具不同，先分清楚再下钻。
