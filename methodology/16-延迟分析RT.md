# 16 延迟分析（RT / 实时延迟）

> CPU 子系统三大空白之三：实时/延迟抖动。与 10（吞吐/热点）是**两个维度**——吞吐看「平均」，延迟看「最坏」和「长尾」。普通 perf 看不出调度延迟尖刺。
> 本文转录自 spec §4「按症状分型（性能回归）」+ §5「知识源与优先级」。

**核心原则（先记住）**：RT/嵌入式场景的痛点是「最坏延迟」不是「平均吞吐」。定位延迟抖动靠三样分层探测：**osnoise** 量化「系统噪声」（谁在打扰这个 CPU）、**timerlat** 量化「调度延迟」（定时器醒来延迟多久）、**hwlat** 量化「硬件/固件噪声」（SMI 等 perf 看不见的停顿）。最后用 `preemptirqsoff`/`wakeup` tracer 找出「最坏延迟的代码来源」。

## 工具一：osnoise tracer —— 系统噪声总览

**识别什么症状**：某 CPU 上实时任务被间歇打扰，想知道「噪声来自哪里」——NMI、硬中断、软中断还是线程干扰。

**关键命令**：

```bash
# 挂 osnoise tracer
echo osnoise > /sys/kernel/tracing/current_tracer
# 配置：在哪些 CPU 跑、周期、时长
echo 2 > /sys/kernel/tracing/osnoise/cpus          # 只在 cpu2 探测
echo 100000 > /sys/kernel/tracing/osnoise/period_us # 周期 100ms
echo 90000  > /sys/kernel/tracing/osnoise/runtime_us
# 读结果
cat /sys/kernel/tracing/trace
```

**怎么读输出**：osnoise 用内核线程循环读 `time()`，两读间隔超过阈值即记一次「噪声」。报告给出**总噪声、最大噪声、CPU 占用百分比**，并按来源分类计数：

- `NMI noise` / `IRQ noise` / `Softirq noise` / `Thread noise` 各一列——哪类计数高，噪声就主要来自哪类。
- `osnoise:nmi_noise` / `osnoise:irq_noise` / `osnoise:softirq_noise` / `osnoise:thread_noise` tracepoint 可拿到「具体是哪个中断/线程在打扰」。

> 出处：`Documentation/trace/osnoise-tracer.rst`（osnoise 原理、配置项、噪声分类）

## 工具二：timerlat tracer —— 调度延迟（IRQ + thread 延迟）

**识别什么症状**：定时器/周期任务「该醒没醒」，想知道「从定时器到期到任务真正跑起来」延迟多少、是 IRQ 延迟还是线程调度延迟。

**关键命令**：

```bash
echo timerlat > /sys/kernel/tracing/current_tracer
echo 1000 > /sys/kernel/tracing/tracing_thresh     # 延迟超过 1000us 才记（阈值）
cat /sys/kernel/tracing/trace
```

**怎么读输出**：timerlat 用一个 hrtimer 周期唤醒线程，报告两段延迟：

- **IRQ latency**：定时器到期 → 硬中断处理完（受关中断、SMI 影响）。
- **Thread latency**：硬中断完 → 线程真正被调度跑起来（受关抢占、优先级、其他任务抢占影响）。

两段分开读：IRQ 延迟高 = 关中断/硬件噪声问题（转 15）；Thread 延迟高 = 调度/优先级问题（转 14）。配 `echo <us> > tracing_thresh` 只记超阈值的，抓长尾尖刺。

> 出处：`Documentation/trace/osnoise-tracer.rst`（timerlat 段：IRQ/thread latency 定义）；rtla 前端见 `tools/tracing/rtla/`

## 工具三：hwlat detector —— 硬件/固件噪声（SMI）

**识别什么症状**：关中断、关抢占都排除了，仍有周期性长停顿（几十 μs 到 ms），怀疑 **SMI（System Management Interrupt）/ 固件**在「偷走」CPU——这类 perf 和 osnoise 都抓不准。

**关键命令**：

```bash
echo hwlat > /sys/kernel/tracing/current_tracer
cat /sys/kernel/tracing/trace
```

**怎么读输出**：hwlat 在**关中断状态下**轮询时间戳，凡检测到「本 CPU 被抢走一段时间」（中断被外部机制屏蔽）即报告。报告里的停顿点就是 SMI/固件噪声——这种停顿**无法靠改内核代码消除**，要改 BIOS/固件设置或换硬件。

> 出处：`Documentation/trace/hwlat_detector.rst`（hwlat 原理与用法）

## 工具四：preemptirqsoff / wakeup tracer —— 找最坏延迟的代码来源

**识别什么症状**：已确认有延迟尖刺，想知道「具体是哪段代码关中断/关抢占最久」或「谁耽误了实时任务醒来」。

**关键命令**：

```bash
# 关抢占/关中断最长区间（找延迟元凶）
echo preemptirqsoff > /sys/kernel/tracing/current_tracer
echo 0 > /sys/kernel/tracing/tracing_max_latency
cat /sys/kernel/tracing/trace        # 跑负载后读：最长关抢占 + 栈

# 谁耽误了最高优先级任务醒来（RT 场景）
echo wakeup_rt > /sys/kernel/tracing/current_tracer
cat /sys/kernel/tracing/trace
```

**怎么读输出**：`preemptirqsoff` 报告 `latency: N us` 最大延迟 + 对应代码栈（栈顶=元凶，转 15）。`wakeup_rt` 追踪「最高优先级任务从被唤醒到真正运行」的延迟，栈指出「是谁/哪段代码在它之前占着 CPU」。

> 出处：`Documentation/trace/ftrace.rst`（preemptirqsoff / wakeup / wakeup_rt tracer）

## 工具五：rtla 用户态前端（免手敲 debugfs）

**识别什么症状**：不想手敲 `current_tracer`，想要 `rtla osnoise/timerlat/hwlat` 一行命令出报告。

**关键命令**：

```bash
# rtla 是内核源码树里的用户态前端（tools/tracing/rtla/）
rtla osnoise top -c 2-3          # 交互式看 cpu2-3 噪声
rtla osnoise hist -c 2-3 -d 10   # 10 秒直方图
rtla timerlat top                # timerlat 交互视图
rtla hwnoise                    # hwlat 前端（较新版本）
```

**怎么读输出**：`rtla osnoise top` 像 `top` 一样实时刷新各噪声源计数；`hist` 出延迟直方图看长尾。底层就是上面 osnoise/timerlat/hwlat tracer，rtla 只是把配置和解析封装好。

> 出处：`tools/tracing/rtla/`（内核树内 rtla 源码与文档）；tracer 本身见 `Documentation/trace/osnoise-tracer.rst`

## 常见根因 + 修复注意

**常见根因**：

- **关中断/关抢占太久**：`local_irq_disable()` / `preempt_disable()` 长区间（→ 15 / 06）。
- **SMI / 固件噪声**：hwlat 抓到、改代码无效的停顿（→ BIOS/固件）。
- **优先级反转 / 优先级配错**：RT 任务被低优先级任务长期阻塞（→ 14）。
- **长临界区**：大锁/spinlock 内长操作，阻塞 RT 任务（→ 07）。
- **周期性重负载**：某个中断/软中断周期性高频触发，制造规律噪声（→ 15）。

**修复注意**：

1. **分层定位，别跳步**：先用 osnoise 看「噪声总量和来源」，再按来源下钻（中断→15、调度→14、SMI→hwlat）。
2. 延迟目标用**最坏/长尾（P99/max）**衡量，不是平均；`tracing_thresh`/`tracing_max_latency` 专门抓最坏。
3. SMI 类停顿改内核无效，明确告诉用户「这是硬件/固件问题」，别在代码里空耗。
4. 修复后用 timerlat 重测 IRQ/thread 两段延迟，确认都降下来。
