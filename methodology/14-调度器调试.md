# 14 调度器调试

> CPU 子系统三大空白之一：调度问题（谁该跑没跑、谁跑太久、迁移到错 CPU、优先级/亲和配错）。
> 本文转录自 spec §4「按症状分型（行为错误/性能回归/挂死）」+ §5「知识源与优先级」。

**核心原则（先记住）**：调度问题不直接崩，表现成三类**症状**——①延迟（该跑没及时跑，RT/交互卡顿）、②CPU 利用率（负载不均衡、某核空转某核积压）、③顺序/亲和（进程跑到了错误的 CPU 或错误的优先级）。定位靠三样：`/proc/sched_debug` 看**快照**、sched tracepoint 看**时序**、`schedstat` 看**统计**。

## 工具一：`/proc/sched_debug` —— 每 CPU 运行队列快照

**识别什么症状**：负载不均衡（某 CPU `nr_running` 高、别的空转）、怀疑进程被迁移到错核、怀疑某进程长期不被调度。

**关键 config / 参数**：

- `CONFIG_SCHED_DEBUG=y`（控制 `/proc/sched_debug` 是否存在，调试内核通常开）。

**关键命令**：

```bash
cat /proc/sched_debug | head -200        # 每 CPU 一节，量大
# 抓重点：
cat /proc/sched_debug | grep -E 'cpu#|nr_running|\.nr_switches|\.nr_load_updates|load'
```

**怎么读输出**：输出按 CPU 分节，每节开头 `cpu#N, ...`，下面是该 CPU 的负载与运行任务列表：

- `nr_running` —— 该 CPU 上正在运行/可运行的任务数；**各 CPU 之间 `nr_running` 严重不均 = 负载均衡问题**。
- 每任务的 `se.exec_start`/`se.sum_exec_runtime`/`se.nr_migrations` —— `nr_migrations` 高说明任务被频繁迁移（可能亲和设置与负载均衡打架）。
- 反复抓几次（`for i in $(seq 5); do cat /proc/sched_debug | grep -A5 'cpu#3'; sleep 1; done`），看哪个 CPU 的 `nr_running` 一直高、哪个一直 0。

> 出处：`CONFIG_SCHED_DEBUG` 与 `/proc/sched_debug` 字段见 `Documentation/scheduler/sched-stats.rst`；调度域/负载均衡概念见 `Documentation/scheduler/sched-domains.rst`

## 工具二：sched tracepoints —— 看切换/唤醒/迁移时序

**识别什么症状**：某进程「该醒没醒」或「被不该的时机抢占」，快照看不出来，要看**事件流**。

**关键命令**：

```bash
# 挂 sched 事件（sched_switch / sched_wakeup / sched_migrate_task）
trace-cmd record -e 'sched:*' -p function_graph -- sleep 5
# 或 perf
perf record -e 'sched:sched_switch,sched:sched_wakeup,sched:sched_migrate_task' -a -- sleep 5
# 只看某进程
echo <pid> > /sys/kernel/tracing/set_event_pid   # 限定进程，排除噪声
```

**怎么读输出**（三个关键事件）：

- `sched_switch`：`prev_comm=X ==> next_comm=Y [cpu=N]`，字段 `prev_state` 是关键——`R`（可运行，被抢占）、`S`（睡眠）、`D`（不可中断睡眠）、`T`（停止）。**prev_state=R 说明是被抢占**（优先级/时间片问题）；`D` 说明是等资源（转 06 挂死/07 死锁）。
- `sched_wakeup`：`comm=X` 被谁唤醒（`pid=N`），看「该醒的进程为什么没及时醒」。
- `sched_migrate_task`：`comm=X migr_from=N to=M`，看「谁把进程迁走了」，配合 `cpuset`/亲和判断是否误迁移。

> 出处：`Documentation/trace/events.rst`（sched 事件组）；trace-cmd 用法见 `Documentation/trace/ftrace.rst`

## 工具三：schedstat / `/proc/<pid>/sched` —— 调度统计

**识别什么症状**：量化「这个进程被调度了多少次、等了多久、被迁移了几次」。

**关键 config / 命令**：

- `CONFIG_SCHEDSTATS=y`（开启后 `/proc/schedstat`、`/proc/<pid>/schedstat` 才有数据）。

```bash
cat /proc/schedstat              # 每 CPU：总运行 jiffies、切换次数、等待时间等
cat /proc/<pid>/schedstat        # 该进程：runnable 时长、切换次数
cat /proc/<pid>/sched            # 该进程的调度策略、优先级、cpus_allowed
cat /proc/<pid>/status | grep -i ctx   # voluntary/involuntary 上下文切换数
```

**怎么读输出**：

- `/proc/<pid>/schedstat` 三列：`se.sum_exec_runtime`（累计运行）、`se.statistics.wait_sum`（累计等待）等——**等待时长异常高** = 该进程长期得不到 CPU。
- `involuntary context switches` 高 = 频繁被抢占/时间片耗尽。
- `/proc/<pid>/sched` 的 `policy`（0=OTHER/CFS、1=FIFO、2=RR、6=DL）、`prio`、`cpus_allowed_list` —— 核对优先级与亲和是否配错。

> 出处：`Documentation/scheduler/sched-stats.rst`（CONFIG_SCHEDSTATS、schedstat 字段）；`Documentation/filesystems/proc.rst`（`/proc/<pid>/sched`、`status` 的 ctx 计数）

## 工具四：优先级 / 亲和 / cpuset —— 配置层面核对

**识别什么症状**：进程跑在错 CPU、优先级被别的进程压制、RT 任务被普通任务抢占。

**关键命令**：

```bash
chrt -p <pid>                  # 看实时优先级/策略
taskset -pc <pid>              # 看亲和掩码
cat /sys/fs/cgroup/cpuset.cpus.effective   # cpuset 生效的 CPU 集合（cgroup v2）
cat /proc/<pid>/status | grep -E 'Cpus_allowed|voluntary'
```

**怎么读输出**：RT 任务 `policy=FIFO/RR` 且 `prio` 高，却仍被抢（`prev_state=R`），查是不是被 `sched_setaffinity` 绑到了繁忙核、或 cpuset 把它和干扰任务放到了同一组。

> 出处：`chrt`/`taskset` 是 util-linux 工具；cpuset 见 `Documentation/admin-guide/cgroup-v2.rst`

## 常见根因 + 修复注意

**常见根因**：

- **优先级错误 / 优先级反转**：RT 任务优先级配低，或被普通任务长期占用 CPU。
- **亲和 / cpuset 配错**：进程被绑到繁忙核或干扰核，`sched_migrate_task` 频繁。
- **负载均衡失衡**：各 CPU `nr_running` 严重不均（魔改负载均衡 / 调度域时引入）。
- **唤醒路径漏了 `wake_up` / 条件变量没通知**：`sched_wakeup` 里目标进程根本没被唤醒。
- **抢占关闭太久**：`preempt_disable()` 长区间，导致其他任务迟迟得不到 CPU（交叉引用 06 挂死）。

**修复注意**：

1. **先定性**：延迟问题 → sched tracepoint + schedstat 等待时长；负载问题 → `/proc/sched_debug` 的 `nr_running` 分布；顺序/亲和 → `/proc/<pid>/sched` 的 policy/prio/cpus_allowed。
2. 调度器改动（CFS 参数、调度类、负载均衡）后，**必跑 sched tracepoint 看一次完整切换时序**，确认 `prev_state` 符合预期。
3. RT 场景配合 `methodology/16-延迟分析RT.md` 的 osnoise/timerlat 量化最坏延迟。
