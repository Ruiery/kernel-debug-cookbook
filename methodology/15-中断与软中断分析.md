# 15 中断与软中断分析

> CPU 子系统三大空白之二：中断/软中断问题——中断风暴、关中断太久、softirq 堆积、下半部设计错误。
> 本文转录自 spec §4「按症状分型（性能回归/挂死）」+ §5「知识源与优先级」。

**核心原则（先记住）**：中断问题分两类，别混——①**中断风暴**：某个 IRQ 疯狂触发，CPU 被中断淹没；②**关中断/软中断太久**：`local_irq_disable()` 或长软中断处理，导致延迟/挂死/RCU stall。先看 `/proc/interrupts` 和 `/proc/softirqs` 定位「哪个源在飙」，再用 irqsoff tracer 量化「关中断最久多长、卡在哪」。

## 工具一：`/proc/interrupts` —— 中断计数与风暴定位

**识别什么症状**：某 CPU 被中断占满、`top` 里 `%si`（软中断）或 `%hi`（硬中断）飙高、系统响应变慢。

**关键命令**：

```bash
cat /proc/interrupts          # 全量中断计数
watch -d cat /proc/interrupts # 动态看哪一行计数在猛涨
```

**怎么读输出**：每行一个 IRQ 源（`NMI`、`LOC` 本地定时器、`RES`、以及各设备 IRQ），后面是**每个 CPU 的累计计数**：

- 某设备 IRQ 行的计数**每秒猛涨成千上万** = 该设备**中断风暴**（驱动没清中断状态 / 电平没拉低 / 误触发）。
- 所有 CPU 的 `LOC`（local timer）都极高 = 定时器中断本身高频，查是否 `CONFIG_HZ` 过高或定时器风暴。
- 观察 `watch -d` 高亮变化，快速锁定是哪个 IRQ。

**辅助**：`cat /proc/irq/<n>/smp_affinity` 看该 IRQ 绑到哪些 CPU（可手动 `echo` 改亲和分散负载，或交给 `irqbalance`）。

> 出处：`Documentation/filesystems/proc.rst`（`/proc/interrupts`、`/proc/irq/<n>/smp_affinity`）

## 工具二：`/proc/softirqs` —— 软中断处理量

**识别什么症状**：`%si` 高、怀疑软中断（NET_RX/TX、TIMER、RCU、SCHED）堆积。

**关键命令**：

```bash
cat /proc/softirqs           # 每 CPU 各 softirq 计数
```

**怎么读输出**：每行一种软中断（`HI`、`TIMER`、`NET_TX`、`NET_RX`、`RCU`、`SCHED`、`TASKLET` 等），后接每 CPU 计数：

- `NET_RX`/`NET_TX` 极高 = 网络软中断处理量大（可能是收包风暴或 NAPI 设计问题）。
- 某 CPU 的某 softirq 计数远高于其他 CPU = 软中断在某核堆积（亲和/负载不均）。
- `TIMER` 极高 = 定时器软中断风暴（大量 `mod_timer` 短周期重排）。

> 出处：`Documentation/filesystems/proc.rst`（`/proc/softirqs`）

## 工具三：irqsoff / preemptirqsoff tracer —— 关中断/关抢占最长时间

**识别什么症状**：延迟尖刺、偶发挂死、RCU stall，怀疑某段代码**关中断**（`local_irq_disable`）或**关抢占**（`preempt_disable`）太久。

**关键命令**：

```bash
# 关中断（irqs disabled）最长时间
echo irqsoff > /sys/kernel/tracing/current_tracer
echo 0 > /sys/kernel/tracing/tracing_max_latency   # 清零历史最大值
cat /sys/kernel/tracing/trace                       # 看最长关中断区间 + 栈
# 关抢占（preemption disabled）最长时间
echo preemptirqsoff > /sys/kernel/tracing/current_tracer
```

**怎么读输出**：`trace` 头部 `latency: N us` 是该 tracer 记录到的**最大延迟**；下面跟的栈就是「关中断/关抢占最久的那段代码」——栈顶函数即元凶。`tracing_max_latency` 记录历史最大值，跑一段负载后再 `cat`，就能抓「最坏情况下的最长关中断」。

> 出处：`Documentation/trace/ftrace.rst`（irqsoff / preemptirqsoff tracer、tracing_max_latency）

## 工具四：定位中断/软中断处理路径

**识别什么症状**：已锁定是哪个 IRQ/softirq，想知道它的处理函数里哪段耗时/卡住。

**关键命令**：

```bash
# 用 function_graph 跟踪某中断处理函数
echo function_graph > /sys/kernel/tracing/current_tracer
echo 'my_irq_handler*' > /sys/kernel/tracing/set_ftrace_filter
# 或看 tasklet/workqueue 下半部
cat /proc/interrupts | grep -i tasklet   # 部分内核版本有 tasklet 统计
```

**怎么读输出**：`function_graph` 的 `DURATION` 列标出中断处理链上哪一步最耗时（交叉引用 10 的 function_graph 读法）；若 handler 本身不长但 `softirq` 后处理长，去查下半部（softirq/tasklet/workqueue）设计。

> 出处：`Documentation/trace/ftrace.rst`（function_graph tracer）

## 常见根因 + 修复注意

**常见根因**：

- **中断风暴**：驱动中断处理函数没清中断状态位（电平/边沿触发配置错），导致 IRQ 一直触发。
- **关中断太久**：`local_irq_disable()` 后长循环/调重函数（魔改里常见）→ 延迟 + hardlockup/RCU stall。
- **softirq 堆积**：软中断处理函数太重，或某核亲和导致软中断集中。
- **下半部设计错**：该放 tasklet/workqueue 的重活放在了硬中断上下文（硬中断里做长操作）。
- **定时器风暴**：大量短周期 timer 反复 `mod_timer`，`TIMER` softirq 飙升。

**修复注意**：

1. **先分型**：`%hi` 高 → `/proc/interrupts` 找风暴源；`%si` 高 → `/proc/softirqs` 找堆积；延迟/挂死 → irqsoff tracer 找最长关中断。
2. 中断上下文（hardirq）**绝不睡眠、绝不做长操作**——重活下沉到 tasklet/workqueue/线程化中断（threaded IRQ）。
3. 关中断区间越短越好；必须关的，用 `local_irq_save/restore` 精确包住最小临界区。
4. 修复后复查 `irqsoff` 的 `tracing_max_latency`，确认最长关中断已降下来。
