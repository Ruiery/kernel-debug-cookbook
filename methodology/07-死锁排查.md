# 07 死锁排查

> 决策树第 1 步「死锁」分型的展开打法：进程 D 状态卡住、lockdep 循环锁依赖告警的识别、定位与根因。
> 本文转录自 spec §4「按症状分型（死锁）」+ §5「知识源与优先级」。

**核心原则（先记住）**：死锁的现场（D 状态进程、hung_task 告警）是「结果」，根因是「锁的获取顺序」。lockdep（`CONFIG_PROVE_LOCKING`）的价值在于它能在死锁**真的发生前**，仅凭出现过的单次锁序就证明「存在死锁可能」——优先用它，别等系统真挂。

## 工具一：lockdep（`CONFIG_PROVE_LOCKING`）—— 循环锁依赖报告

**识别什么症状**：dmesg 出现 `WARNING: possible circular locking dependency detected`，或进程 D 状态卡住、`INFO: task ... blocked for more than ... seconds`（hung_task）指向等锁。

**关键 config**：`CONFIG_PROVE_LOCKING=y`（自动 select `CONFIG_LOCKDEP`）。配套 `CONFIG_DEBUG_KERNEL`、`CONFIG_KALLSYMS` 出完整符号栈。

**怎么读输出**：循环锁依赖报告分几段，按顺序读：

1. `possible circular locking dependency detected` 开头，点出「哪个任务在拿哪把锁」。
2. `which lock is being acquired:` —— 当前想拿的锁。
3. `but task is already holding lock:` —— 已经持有的锁（矛盾所在）。
4. 一条 `->` 链展示锁的获取顺序（如 `L1 -> L2 -> ... -> L1`），这就是逆序依赖形成的环。
5. 每把锁名后带 `{....}` 状态位，标记这把锁的历史使用上下文：
   - `.` = irq 关闭且非 irq 上下文；`-` = irq 上下文获取；`+` = irq 开启获取；`?` = irq 上下文且 irq 开启。
   - 用途：看锁是否被中断上下文用过，判断是不是「irq-safe 锁 vs irq-unsafe 锁」逆序（spin_lock 里被软中断再抢同类锁）。
6. `other info that might help us debug this:` 给出各任务当时持锁/等锁的栈。

把这条 `->` 环对照你的加锁代码，环上任意一处调换锁序即可断开。

> 出处：`Documentation/locking/lockdep-design.rst`（lock-class、状态位 `{....}` 语法、依赖规则）

## 工具二：`/proc/lockdep` 系列 —— 看锁类与依赖链

**何时用**：lockdep 没报、但怀疑锁序问题时，直接查运行时锁依赖图；或怀疑锁类泄漏/未初始化。

**关键命令**：

- `cat /proc/lockdep` —— 所有已注册的锁类（lock-class）。
- `cat /proc/lockdep_chains` —— 已观察到的锁依赖链（L1 -> L2 的序）。
- `cat /proc/lockdep_stats` —— 统计（如 `grep "lock-classes" /proc/lockdep_stats` 看锁类数量是否达上限 8191，持续增长=泄漏）。
- `cat /proc/lock_stat` —— 每把锁的竞争统计（谁在抢、持锁时长）。

**怎么读输出**：在 `lockdep_chains` 里找「同一对锁以相反顺序出现」的两条链，就是 ABBA 环的证据；`lockdep` 里对照锁类数量判断是否 `spin_lock_init()` 漏初始化（同一数组锁被当多个类，导致锁类爆表）。

> 出处：`Documentation/locking/lockdep-design.rst`（Troubleshooting：`/proc/lockdep`、`/proc/lockdep_stats`、MAX_LOCKDEP_KEYS）

## ABBA 死锁原理

两个任务按**相反顺序**拿同一对锁即死锁：

```
task A: lock(L1) → lock(L2)
task B: lock(L2) → lock(L1)
```

A 持 L1 等 L2，B 持 L2 等 L1，互相等对方释放，谁都不能前进。lockdep 的强项：只要「A 拿过 L1→L2」和「B 拿过 L2→L1」这两段简单锁序**各自出现过一次**（不必真的同时发生），就能推出这个环存在死锁可能，实现 100% 闭包证明。

## 常见根因 + 修复注意

**常见根因**：

- **锁序不一致（ABBA）**—— 最常见的死锁来源。
- **持锁睡眠**—— 拿着 mutex/spinlock 时调用了会睡眠的函数（等待被另一把锁保护的资源）。
- **`spin_lock` 里调会睡眠的函数**—— `mutex_lock()`、`kmalloc(GFP_KERNEL)`、`copy_from_user()` 等，自旋锁上下文不能睡。
- **同锁递归**—— 同一任务对同一把非递归锁二次加锁（self-deadlock）。

**修复注意**：

1. **统一锁序**（根本解法）：定义全局一致的加锁顺序，任何路径都按同一顺序取多把锁。
2. 用 `mutex_trylock()` 取代 `mutex_lock()`，拿不到就释放已有锁重试，避免阻塞成环。
3. 减少锁嵌套，能一把锁解决不叠两把。
4. 辅助检测开关：
   - `CONFIG_DEBUG_ATOMIC_SLEEP` —— 在原子上下文（spinlock / rcu_read_lock / 关抢占 / 中断）里睡眠会立刻 WARN。
   - `CONFIG_DEBUG_SPINLOCK` —— 自旋锁未初始化、自旋时睡眠等误用检测。
   - `CONFIG_DEBUG_MUTEXES` —— mutex 误用检测。
   - `CONFIG_DEBUG_WW_MUTEX_SLOWPATH` —— wound/wait mutex 的完整路径校验。
5. 用 `lockdep_assert_held()` 在关键路径断言「此锁必须已持有」，把隐式契约变成运行时可查。
