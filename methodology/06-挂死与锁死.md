# 06 挂死与锁死

> 决策树第 1 步「挂死/锁死」分型的展开打法：softlockup / hardlockup / hung_task / rcu stall 四类告警的识别、定位与根因。
> 本文转录自 spec §4「按症状分型（挂死/锁死）」+ §5「知识源与优先级」。

**核心原则（先记住）**：挂死现场只告诉你「哪个 CPU/任务卡了」，不告诉你「卡在哪一行」。识别靠看门狗（watchdog）告警，定位靠 SysRq 全 CPU backtrace + ftrace 找卡点函数。soft 和 hard 是两种完全不同的卡法，先分清楚再动手。

## 工具一：softlockup / hardlockup 检测器（watchdog）

**识别什么症状**：内核在某 CPU 上长时间原地打转，整机或单核无响应。

- **softlockup** = 内核态循环超过约 **20 秒**（默认 `2 * watchdog_thresh`），不给其他任务调度机会。中断仍能响应。
- **hardlockup** = CPU 内核态循环超过约 **10 秒**（默认 `watchdog_thresh`），连 NMI 中断都不响应。

**关键 config / 参数**：

- 编译：`CONFIG_SOFTLOCKUP_DETECTOR`、`CONFIG_HARDLOCKUP_DETECTOR`（两者在 `CONFIG_LOCKUP_DETECTOR` 下）。
- 启动参数 / sysctl：
  - `softlockup_panic=1`（或 sysctl `kernel.softlockup_panic`；编译选项 `CONFIG_BOOTPARAM_SOFTLOCKUP_PANIC`）—— softlockup 时 panic。
  - `hardlockup_panic=1`（sysctl `kernel.hardlockup_panic`）或 `nmi_watchdog=1`（hardlockup 检测器即 NMI watchdog；`nmi_watchdog=panic` 超时直接 panic；编译选项 `CONFIG_BOOTPARAM_HARDLOCKUP_PANIC`）。
  - `watchdog_thresh=`—— hardlockup 阈值（秒），softlockup 阈值为其两倍；`0` 同时关掉两个检测器，默认 10 秒。
  - `softlockup_all_cpu_backtrace=1` / `hardlockup_all_cpu_backtrace=1`—— 告警时顺带 dump 所有 CPU 的 backtrace。

**怎么读输出**：dmesg 里两条标志性告警：

- softlockup：`BUG: soft lockup - CPU#N stuck for 22s! [进程名:pid]`，后面跟当前 CPU 的栈。
- hardlockup：`Watchdog detected hard LOCKUP on cpu N`，来自 NMI 路径。

soft vs hard 的区别就是「中断还能不能进」：soft 是调度不动（关抢占/关 bottom half/自旋），hard 是连 NMI 都不响应（关中断太久或中断上下文里死循环）。

> 出处：`Documentation/admin-guide/lockup-watchdogs.rst`；参数见 `Documentation/admin-guide/kernel-parameters.rst`

## 工具二：hung_task 检测器

**识别什么症状**：某个进程卡在 **D 状态（uninterruptible sleep）** 超过阈值，长时间没被调度——典型是等锁、等 IO、等不可达资源。

**关键 config / 参数**：

- 编译：`CONFIG_DETECT_HUNG_TASK`（需 `CONFIG_SMP`）。
- sysctl / 启动参数：
  - `hung_task_timeout_secs`（sysctl `kernel.hung_task_timeout_secs`）—— D 状态超过该秒数报 warning，默认 120。
  - `hung_task_panic=1`（sysctl `kernel.hung_task_panic`；编译选项 `CONFIG_BOOTPARAM_HUNG_TASK_PANIC`）。
  - `hung_task_check_interval_secs`、`hung_task_warnings`、`hung_task_all_cpu_backtrace`。

**怎么读输出**：`INFO: task 进程名:pid blocked for more than 120 seconds.`，后面是 `Not tainted` 版本号 + 该任务的 `call trace`。栈顶通常就是它卡住的函数（等哪把锁 / 哪个调用）。

> 出处：`Documentation/admin-guide/sysctl/kernel.rst`（hung_task_* 小节）；参数见 `Documentation/admin-guide/kernel-parameters.rst`

## 工具三：RCU CPU stall detector

**识别什么症状**：RCU grace period 长时间收不齐（读侧临界区卡住、或 RCU kthread 被饿死），系统可能逐步耗光内存后挂起。

**关键 config / 参数**：

- `CONFIG_RCU_CPU_STALL_TIMEOUT`—— 默认 21 秒；运行时改 `/sys/module/rcupdate/parameters/rcu_cpu_stall_timeout`。
- `rcupdate.rcu_cpu_stall_suppress`—— 关掉 stall 检测（sysfs 同名参数）。
- 加速定位：`CONFIG_RCU_CPU_STALL_CPUTIME`（或 `rcupdate.rcu_cpu_stall_cputime=1`）额外打 hardirq/softirq/csw 计数，用于分辨「关中断 / 关 bottom half / 关抢占」哪种卡法。

**怎么读输出**：`INFO: rcu_sched detected stalls on CPUs/tasks:` 后跟每核一行（如 `2-...: (3 GPs behind) idle=06c/0/0 softirq=1453/1455 fqs=0`）+ 各 CPU 栈。关键信息：

- `(N GPs behind)` = 该 CPU 已经 N 个 grace period 没响应。
- `(0 ticks this GP)` = 本周期内没收到任何调度时钟中断 → 关中断或关 bottom half。
- `softirq=` 后一个数跨多次告警不变 → RCU softirq 跑不动（关中断自旋，或 -rt 下高优先级进程饿死 softirq）。
- 带 `CONFIG_RCU_CPU_STALL_CPUTIME` 时，`cputime:` 三列分别对应该核 hardirq / softirq / 系统态耗时，结合 `number:` 的 csw=0 可判关抢占。

> 出处：`Documentation/RCU/stallwarn.rst`

## 工具四：SysRq —— 挂死时拿全 CPU backtrace

**何时用**：系统还活着（NMI/中断能进）但某处卡住时，用魔术键强制 dump 现场，不依赖正常调度。

**关键命令**（键盘 `ALT-SysRq-<key>`，或等价 `echo <key> > /proc/sysrq-trigger`）：

- `echo t > /proc/sysrq-trigger` —— dump 所有任务及状态（谁 D 状态、谁 RUNNING 卡着）。
- `echo w > /proc/sysrq-trigger` —— 只 dump **D 状态（阻塞）** 的任务。
- `echo l > /proc/sysrq-trigger` —— 所有 CPU 的 backtrace（关键：看哪个 CPU 卡在哪）。
- `echo d > /proc/sysrq-trigger` —— dump 所有被持有的锁（配合死锁排查）。
- `echo m > /proc/sysrq-trigger` —— 内存信息。

**怎么读输出**：`l` 的输出里，反复出现、不前进的那个函数地址/符号，就是卡点；和 `t`/`w` 里 D 状态任务的栈顶对照，即定位是谁持锁/谁死循环。

> 出处：`Documentation/admin-guide/sysrq.rst`（command key 表）

## 工具五：ftrace function tracer —— 找卡住的函数

**何时用**：watchdog 告警只给单次快照，或想持续看「卡在哪个函数、是否在循环」。

**关键命令**：

- `CONFIG_FUNCTION_TRACER` + 挂 function tracer：`echo function > /sys/kernel/tracing/current_tracer`（或 function_graph 看调用/返回，但 function_graph 会加重 interrupt handler 耗时，本身可能诱发 RCU stall，慎用）。
- 对怀疑的函数/模块设 filter，缩小范围。

**怎么读输出**：读 `/sys/kernel/tracing/trace`，看最后一次进入后迟迟没有返回的那个函数，即嫌疑卡点。

> 出处：`Documentation/trace/ftrace.rst`（function / function_graph tracer）

## 常见根因 + 修复注意

- **关中断 / 关 bottom half 太久**：`local_irq_disable()` / `local_bh_disable()` 后长循环或调重函数 → hardlockup 或 rcu stall（`0 ticks this GP`、`softirq` 不变）。
- **关抢占太久 / 自旋锁里死循环**：`preempt_disable()` 或 spinlock 内长循环 → softlockup。
- **RCU 读侧临界区睡眠**：`rcu_read_lock()` 内调会睡眠的函数 → 阻塞 grace period → rcu stall。
- **非 `CONFIG_PREEMPTION` 内核长忙等**：无 `cond_resched()` 的内核态长循环 → softlockup。

**修复注意**：先拿 `l`/`t` backtrace 定位，别急着 `panic=1` 了事。长循环里加 `cond_resched()`；中断/自旋锁上下文绝不睡眠、不做长操作；`rcu_read_lock()` 临界区不睡眠；排查时优先确认是「关中断」还是「关抢占」——两者修法不同。
