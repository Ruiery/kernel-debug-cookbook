# 17 栈溢出定位

> 崩溃细分里独立于「内存生命周期」的一种根因：内核栈用超了。深递归 / 大栈帧 / 中断栈溢出。
> 本文转录自 spec §4「崩溃细分」+ §5「知识源与优先级」。

**核心原则（先记住）**：内核栈极小（进程栈通常 8KB/16KB，`CONFIG_THREAD_INFO_IN_TASK` 后更多，但**中断栈独立且更小**），栈溢出是「崩溃」的一种独立根因——不是内存被写坏，而是栈空间本身用超，覆盖了栈下/相邻数据。表现为「看起来随机的 oops」（破坏了别的数据）或明确的 `BUG: stack guard page was hit`。先确认「是不是栈溢出」，再找「哪个大栈帧/递归」。

## 工具一：`CONFIG_VMAP_STACK` + guard page —— 溢出当场抓现行

**识别什么症状**：随机 oops、栈指针指向非法地址、或崩溃现场 `RIP` 在栈相关路径；怀疑深递归/大局部变量。

**关键 config**：

- `CONFIG_VMAP_STACK=y`（x86 等架构默认）—— 用 `vmalloc` 映射内核栈，栈顶/栈底放 **guard page**（不可访问页）。栈一溢出踩到 guard page 立即 oops，而不是静默破坏相邻数据。

**怎么读输出**：dmesg 出现 `BUG: stack guard page was hit at ... (stack is ...)`，或 oops 现场 `RIP` 落在栈附近 + `#PF`（page fault）在 guard page 地址——**基本锁定栈溢出**，且给出了「是谁踩了 guard page」。

> 出处：`CONFIG_VMAP_STACK` 见 `lib/Kconfig.debug`；guard page 机制见 `Documentation/admin-guide/kernel-parameters.rst`（相关参数）

## 工具二：`CONFIG_STACKPROTECTOR` —— canary 检测栈越界

**识别什么症状**：函数返回前栈被越界写（红区写穿），想知道「是哪个函数被溢出覆盖了 canary」。

**关键 config**：

- `CONFIG_STACKPROTECTOR=y`（弱）/ `CONFIG_STACKPROTECTOR_STRONG=y`（强，覆盖更多函数）—— 在栈帧里放 **canary（金丝雀）**，函数返回前校验；被越界写破坏则 panic。

**怎么读输出**：panic 消息 `Kernel panic - not syncing: stack-protector: Kernel stack is corrupted in: <function>`，**直接给出被溢出的函数名** `<function>`——它就是「被写穿栈」的那个函数，沿它的调用链找大栈帧。

> 出处：`CONFIG_STACKPROTECTOR` / `CONFIG_STACKPROTECTOR_STRONG` 见 `lib/Kconfig.debug`

## 工具三：`CONFIG_DEBUG_STACKOVERFLOW` / `DEBUG_STACK_USAGE` —— 栈用量监测

**识别什么症状**：不知道栈用了多少、离上限多近，想量化「哪条路径最费栈」。

**关键 config**：

- `CONFIG_DEBUG_STACKOVERFLOW=y` —— 运行时检查栈溢出（某些架构在 irq/异常路径检查）。
- `CONFIG_DEBUG_STACK_USAGE=y` —— 记录每 CPU 栈的最大用量。

**怎么读输出**：开启后，可用 debugfs / sysfs 查看栈用量峰值（如 `/sys/kernel/debug/tracing/` 相关或 `kernel/sched` 的栈用量统计），找出**哪条调用链最逼近栈上限**，针对性瘦身。

> 出处：`CONFIG_DEBUG_STACKOVERFLOW` / `CONFIG_DEBUG_STACK_USAGE` 见 `lib/Kconfig.debug`

## 工具四：`CONFIG_SCHED_STACK_END_CHECK` —— 调度时检查栈越界

**识别什么症状**：越界发生在睡眠/调度点附近，想在被调度器「复位」前抓到。

**关键 config**：

- `CONFIG_SCHED_STACK_END_CHECK=y` —— 每次调度时检查栈底哨兵（stack end magic），被写坏即 `WARN`。

**怎么读输出**：dmesg 出现 `WARNING: ... stack end ... corrupted` 之类，指出「某个进程的栈底已被越界写」，配 `dump_stack` 拿调用栈。

> 出处：`CONFIG_SCHED_STACK_END_CHECK` 见 `lib/Kconfig.debug`

## 工具五：找「谁用了大栈」—— 大栈帧 / 递归定位

**识别什么症状**：已确认栈溢出，要定位是「哪个函数栈帧太大」还是「递归没界」。

**关键命令**：

```bash
# 编译期看栈帧大小（需要 CONFIG_FRAME_WARN / gcc 的 -Wframe-larger-than）
make ... W=1        # 触发 -Wframe-larger-than 告警，报出超阈值的大栈帧函数
# 运行时看调用链栈深
echo function_graph > /sys/kernel/tracing/current_tracer
echo 'suspect_func*' > /sys/kernel/tracing/set_ftrace_filter
cat /sys/kernel/tracing/trace    # 看递归深度 / 调用链长度
```

**怎么读输出**：

- `-Wframe-larger-than=N`（`CONFIG_FRAME_WARN` 默认 1024/2048）编译告警会**列出所有栈帧超过 N 字节的函数**——逐个看，找局部大数组/大结构体。
- `function_graph` 里同一函数反复嵌套出现（无界递归）或某条链特别深，即递归元凶。

**常见大栈来源**：局部大数组/大结构体、深递归、`alloca`/VLA（变长数组，内核禁用）、巨长参数列表、内联展开后叠加。

> 出处：`-Wframe-larger-than` / `CONFIG_FRAME_WARN` 见 `lib/Kconfig.debug`；function_graph 见 `Documentation/trace/ftrace.rst`

## 常见根因 + 修复注意

**常见根因**：

- **深递归**：无界/有界但太深的递归（文件系统路径、树遍历），每次调用压一层栈。
- **大局部变量**：函数里放了大数组/大结构体（如 `char buf[8192]` 在栈上）。
- **中断栈溢出**：中断处理路径里用了大栈帧，而**中断栈比进程栈更小**（`CONFIG_IRQSTACKS`），进程栈够用但中断栈溢出。
- **内联膨胀**：编译器把多个大栈帧函数内联进一个函数，单帧栈用量暴涨。
- **魔改引入**：把用户态思维（大 buffer、递归）带进内核，或改了调用链深度。

**修复注意**：

1. **先确认类型**：`stack guard page was hit` / `stack-protector` panic = 栈溢出（区别于 KASAN 的内存越界）；再用 `-Wframe-larger-than` 找具体大栈帧。
2. **大 buffer 改动态分配**：`char buf[8192]` → `kmalloc`；或移到堆上/缩小。
3. **递归改迭代**：深递归改显式栈/循环，或限制深度。
4. **中断路径尤其警惕**：中断上下文绝不用大栈帧（中断栈独立且小），重活下沉到线程。
5. 修复后用 `CONFIG_DEBUG_STACK_USAGE` 复测栈用量峰值，确认降下来。
